Training topics

ConsentThe compliance problem

A common pattern: RUM's session cookie (_dd_s) is created the moment the page loads, before any consent banner is answered. Session Replay is correctly gated behind consent — but the cookie itself isn't, and some EU jurisdictions' ePrivacy enforcement treats any non-essential cookie, including a "technical" monitoring cookie, as requiring consent.

The ask: keep full error visibility (the team is replacing Sentry, which needs 100% error capture) while creating zero client-side storage until a user opts in.

StoragesessionPersistence: cookie vs local-storage vs memory

RUM's sessionPersistence init option controls where the SDK keeps its session state:

DD_RUM.init({
  ...
  sessionPersistence: 'local-storage', // or 'cookie' | 'memory'
})
ModeCreates a cookie?Survives refresh?Shared across tabs?
cookieYes (_dd_s)YesYes
local-storageNoYesYes
memoryNoNo — new sessionNo — separate session per tab

Try all three in the Storage Inspector tab, then use the Multi-tab test tab to see why memory risks inflating session counts for a multi-tab workflow, while local-storage doesn't.

If both RUM and Logs SDKs are on the same page, Datadog requires them to use the same sessionPersistence value.

GateGating with setTrackingConsent

The tracking-consent API lets you initialize the SDK once — so it's ready to go — without it writing or sending anything until the user answers:

DD_RUM.init({ ..., trackingConsent: 'pending' })
// later, from your CMP / banner:
DD_RUM.setTrackingConsent('granted')      // starts writing storage + sending data
DD_RUM.setTrackingConsent('not-granted')  // stays fully inert, no storage

Consent isn't remembered by the SDK across page loads — your app re-applies the user's saved choice (from your own CMP) on every load.

The banner at the top of the Storage Inspector tab drives this live: watch the storage cards stay empty until you click Accept.

TabsMulti-tab & refresh session stability

A travel-booking-style flow commonly opens several tabs and refreshes mid-session. That's exactly where memory persistence falls apart: it lives in that one JS heap, so a new tab — or a refresh — has no way to see the old session ID and simply starts a new one.

The Multi-tab test tab uses a BroadcastChannel to compare the live RUM session ID across every open tab of this page, so you can see the effect directly instead of taking it on faith.

ErrorsThe always-on error-tracking backup plan

If the business also wants 100% error capture even pre-consent — matching how event-based tools like Sentry behave — RUM itself isn't the right tool for that slice, since it's intentionally gated by consent end-to-end.

The pattern: run the Logs Browser SDK as an independent, always-on error pipe with sessionPersistence: 'local-storage' (never a cookie), separate from RUM's consent gate:

DD_LOGS.init({
  ...
  sessionPersistence: 'local-storage',
  trackingConsent: 'granted', // always on
  forwardErrorsToLogs: true,
})
// RUM stays gated:
DD_RUM.init({ ..., trackingConsent: 'pending' })

Try it in the Error capture tab — throwing an error is captured by the Logs pipe regardless of the RUM consent state shown at the top of the page.

Legal⚠️ Not a compliance guarantee

This is an engineering lab, not legal advice. Switching from a cookie to local-storage removes an HTTP cookie — but the EU ePrivacy Directive (Art. 5(3)) governs "storing information, or gaining access to information already stored, in the terminal equipment of a subscriber or user," which several national regulators (including some Nordic DPAs) read as covering any client-side storage mechanism, not literally just cookies named "cookie."

In other words: a strict regulator may still require consent before writing to localStorage. Confirm the specific jurisdiction's interpretation with the customer's legal/DPO before presenting sessionPersistence: 'local-storage' as a full fix rather than a mitigation.
