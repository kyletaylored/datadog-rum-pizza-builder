    What happens if you send browser telemetry to Datadog using only standard OpenTelemetry — no RUM SDK? This lab runs the real thing: @opentelemetry/browser-sdk + @opentelemetry/browser-instrumentation, against the same pizza wizard.

    startBrowserSdk() starts a logs pipeline and a traces pipeline. Most instrumentations emit log records; fetch and xhr emit spans. Each signal has its own exportConfig.url, so traces and logs can go to different endpoints.

    startBrowserSdk({
  serviceName: 'datadog-rum-pizza-otlp',
  serviceVersion: cfg.version,
  resourceAttributes: {
    'datadog.application.id': cfg.applicationId,
  },
  traces: {
    processors: [sessionSpans, documentSpans, liveTable],
    exportConfig: { url: 'https://otlp.<site>/v1/traces?dd-api-key=<client token>' },
  },
  logs: {
    processors: [sessionLogs, documentLogs, liveTable],
    exportConfig: { url: 'https://otlp.<site>/api/v2/otlplogs?dd-api-key=<client token>' },
  },
});

    Sending to Datadog is off by default. Turn it on from the Config tab.

    A LogRecordProcessor and a SpanProcessor registered ahead of the OTLP exporters render every log and finished span into the table below before it's exported — the OpenTelemetry version of the RUM SDK's beforeSend. The SDK's session and document processors run first and stamp session.id and browser.document.url.full (the page the event happened on, hash included) on both.

    Every log and span also prints to devtools via ConsoleLogRecordExporter / ConsoleSpanExporter — the same one the official getting-started guide uses. Toggle it from the Config tab.

    Direct sends from the browser to otlp.<site>, with the RUM app's public client token in the dd-api-key query parameter (a header would add a CORS preflight to every export). It only works if the intake answers the browser's CORS check for this origin. Check devtools › Network for the v1/traces and otlplogs requests.

    Proxy sends to a local relay (npm run proxy) that adds the key server-side, so CORS never applies. In either mode, the traces and logs fields override one signal's endpoint, for example to send traces to your own collector. An override URL that already has a dd-api-key keeps it.

    Exported log records become RUM events, not logs. In RUM Explorer, query service:datadog-rum-pizza-otlp: each page load is one session and one view, with actions, resources and vitals under it.

    view.url is browser.document.url.full, and view.name is its path. A hash change updates view.url on later events but doesn't start a new view. Without datadog.application.id or session.id, the same records land in Log Explorer instead.

    Measured on 2026-11-04 by removing one piece at a time. The minimum: logs exported to /api/v2/otlplogs with the client token, plus these three attributes.

    resourceAttributes: { 'datadog.application.id': applicationId },
logs: {
  processors: [
    createSessionLogRecordProcessor(sessionManager),     // session.id
    createDocumentLogRecordProcessor(documentProvider),  // browser.document.url.full
  ],
  exportConfig: { url: 'https://otlp.<site>/api/v2/otlplogs?dd-api-key=<client token>' },
},

    "Fake backend call" on the results screen gives two rows: a span row from the fetch instrumentation (status, duration, trace ID) and a browser.resource_timing row for the same request.

    propagateTraceHeaderCorsUrls: [/.*/] adds the span's traceparent header to every cross-origin request, so the server has to allow it in its CORS preflight. httpbin.org does. In devtools › Network, its response body echoes the header back, with the same trace ID as the row.
