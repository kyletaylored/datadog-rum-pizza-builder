Training topics

ConsentThe compliance problem

A common pattern: RUM's session cookie (_dd_s) is created the moment the page loads, before any consent banner is answered. Session Replay is correctly gated behind consent — but the cookie itself isn't, and some EU jurisdictions' ePrivacy enforcement treats any non-essential cookie, including a "technical" monitoring cookie, as requiring consent.

The ask: keep full error visibility (the team is replacing Sentry, which needs 100% error capture) while creating zero client-side storage until a user opts in.

 StoragesessionPersistence: cookie vs local-storage vs memory

RUM's sessionPersistence init option controls where the SDK keeps its session state:

DD_RUM.init({
  ...
  sessionPersistence: 'local-storage', // or 'cookie' | 'memory'
})
ModeCookie?Refresh-safe?Multi-tab safe?
cookieYesYesYes
local-storageNoYesYes
memoryNoNoNo

"Refresh-safe" and "multi-tab safe" mean the session ID stays the same instead of minting a new one — cookie uses _dd_s, the others use no cookie at all.

Try all three in the Storage Inspector tab, then use the Multi-tab test tab to see why memory risks inflating session counts for a multi-tab workflow, while local-storage doesn't.

If both RUM and Logs SDKs are on the same page, Datadog requires them to use the same sessionPersistence value.

 GateGating with setTrackingConsent

The tracking-consent API lets you initialize the SDK once — so it's ready to go — without it writing or sending anything until the user answers:

DD_RUM.init({ ..., trackingConsent: 'pending' })
// later, from your CMP / banner:
DD_RUM.setTrackingConsent('granted')      // starts writing storage + sending data
DD_RUM.setTrackingConsent('not-granted')  // stays fully inert, no storage

Consent isn't remembered by the SDK across page loads — your app re-applies the user's saved choice (from your own CMP) on every load.

The banner at the top of the Storage Inspector tab drives this live: watch the storage cards stay empty until you click Accept.

 TabsMulti-tab & refresh session stability

A travel-booking-style flow commonly opens several tabs and refreshes mid-session. That's exactly where memory persistence falls apart: it lives in that one JS heap, so a new tab — or a refresh — has no way to see the old session ID and simply starts a new one.

The Multi-tab test tab uses a BroadcastChannel to compare the live RUM session ID across every open tab of this page, so you can see the effect directly instead of taking it on faith.

 ErrorsThe always-on error-tracking backup plan

If the business also wants 100% error capture even pre-consent — matching how event-based tools like Sentry behave — RUM itself isn't the right tool for that slice, since it's intentionally gated by consent end-to-end.

The pattern: run the Logs Browser SDK as an independent, always-on error pipe with sessionPersistence: 'local-storage' (never a cookie), separate from RUM's consent gate:

DD_LOGS.init({
  ...
  sessionPersistence: 'local-storage',
  trackingConsent: 'granted', // always on
  forwardErrorsToLogs: true,
})
// RUM stays gated:
DD_RUM.init({ ..., trackingConsent: 'pending' })

Try it in the Error capture tab — throwing an error is captured by the Logs pipe regardless of the RUM consent state shown at the top of the page.

 ErrorsReplacing Sentry: what Error Tracking needs

The customer is moving off Sentry and needs 100% error capture, cookie-free, before any consent is given. The Logs SDK covers that — but only for errors that arrive with a stack trace.

Datadog Error Tracking turns a log into an issue when the log carries error.stack, grouping and titling it by error.kind and error.message. A status:error log with no stack stays a log line and never becomes an issue:

// becomes an issue — real Error, so a real stack
try { risky() } catch (err) {
  DD_LOGS.logger.error('Checkout failed', { step }, err)
}

// stays a log line — no Error object, no stack
DD_LOGS.logger.error('Checkout failed')
console.error('Checkout failed')

Uncaught exceptions, unhandled promise rejections and failed network requests are picked up automatically by forwardErrorsToLogs: true, with stacks, and need no instrumentation at all.

The Error capture tab fires each source and reports what the SDK actually built for it, so the coverage claim is measured rather than assumed.

 SessionsAvoiding inflated session counts

sessionPersistence: 'memory' is cookie-free, but it keeps the session in a JS variable — so every tab and every refresh starts a brand-new session. On a travel-booking site, where multiple tabs and reloads are normal, that inflates session counts against a number the customer actually reports on.

So rather than putting all traffic on memory, split the two pipes by what they need:

PipeRunsStorage
Logs + Error TrackingAlwaysCookie-free
RUM + ReplayPost-consentcookie

Errors never needed a stable session ID to be useful, so the always-on pipe can be stateless. RUM only exists after consent, where a cookie is allowed and session counts stay honest. No inflation, no coverage gap.

If the customer would rather keep one pipe, local-storage gives stable sessions with no cookie — but read the Legal note below first, because a strict regulator may treat any client-side storage as requiring consent anyway.

 Legal⚠️ Not a compliance guarantee
This is an engineering lab, not legal advice.

Switching from a cookie to local-storage removes an HTTP cookie — but the EU ePrivacy Directive (Art. 5(3)) governs "storing information, or gaining access to information already stored, in the terminal equipment of a subscriber or user," which several national regulators (including some Nordic DPAs) read as covering any client-side storage mechanism, not literally just cookies named "cookie."

In other words: a strict regulator may still require consent before writing to localStorage. Confirm the specific jurisdiction's interpretation with the customer's legal/DPO before presenting sessionPersistence: 'local-storage' as a full fix rather than a mitigation.

      Does this actually replace Sentry? Error-source coverage

      "100% error capture" is the requirement, so the question worth answering precisely is which error sources this cookie-free pipe turns into Error Tracking issues, not just log lines. Datadog's Error Tracking processes a log into an issue when the log carries a stack trace (error.stack); error.kind and error.message are what it groups and titles issues by. A log with status:error and no stack stays a log line forever.

      That distinction is the whole risk in this migration: it's the difference between having 100% error coverage and believing you do. Fire each source and read the measured result — nothing here is asserted, it's whatever the SDK actually builds in this browser.

      Error source origin error.kind Stack? Result

      The two that don't make it are the ones to warn the team about. console.error("some string") and logger.error("some message") both produce a status:error log with no stack trace, so neither ever becomes an issue. Codebases migrating off Sentry tend to be full of exactly these, because Sentry.captureMessage() accepted them. Passing the real Error object — logger.error(msg, ctx, err) — is what makes the difference.

      Recommended shape for a strict-consent deployment

      This is the architecture the coverage table supports, and it avoids needing sessionPersistence: 'memory' for all traffic:

      PipeWhen it runsStorageJob
      Logs + Error Tracking Always, from first paint local-storage or memory — never a cookie 100% error capture, the Sentry replacement
      RUM + Session Replay Only after technical-cookie consent cookie Performance, funnels, replays, accurate session counts

      The reason to split them rather than run RUM on memory everywhere: memory holds the session in a JS variable, so every tab and every refresh mints a brand-new session ID. For a travel-booking site — where opening several tabs and reloading is normal behavior — that inflates session counts against a real number the customer cares about. Prove it to yourself on the Multi-tab test tab: switch to memory, open a second tab, and watch the session IDs diverge.

      Splitting the pipes sidesteps the trade-off entirely. Errors never needed a stable session ID to be useful, so the always-on pipe can be cookie-free and stateless; RUM only ever exists post-consent, where a cookie is permitted and session counts stay honest.
