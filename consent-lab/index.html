      Always-on error capture, independent of consent

      The Logs SDK on this page is initialized independently of the consent banner on the Storage inspector tab: it runs from first paint with trackingConsent: 'granted' and forwardErrorsToLogs: true, whatever RUM's consent state is. That's the always-on backup plan — 100% error capture before anyone clicks anything.

      Whether it's cookie-free is not up to the Logs SDK. Both SDKs on a page share one session manager and one _dd_s store, so Logs uses whatever sessionPersistence RUM uses — this page passes the mode you picked to both. Check the Storage inspector in cookie mode and you'll see a single _dd_s carrying logs=1&rum=1. Going cookie-free is therefore a whole-page decision, not something you can do for the error pipe alone.

      Is every error source actually covered? Error-source coverage

      An error log leaving the Browser Logs SDK does not necessarily become an Error Tracking issue. Browser errors have two separate front doors into Error Tracking, and they have different requirements:

      Front doorFed byRequirementsAvailable pre-consent?
      Frontend Error Tracking RUM Browser SDK Error source is custom, source, report or console, and it carries a stack trace No — RUM is consent-gated end to end
      Error Tracking for Logs Logs Browser SDK (v4.36.0+, forwardErrorsToLogs: true) A service, an error-level status, and either error.kind or a valid error.stack Yes — cookie-free, and enabled separately for the org

      So "we can see the error in the Logs Explorer" and "we have an Error Tracking issue" are two different claims, and the second is the one that actually determines whether error-tracking coverage is real. Three attributes decide it:

      • service — the SDK attaches this from init(), so it's the one requirement you can't forget.
      • An error-level status — error, critical, alert or emergency. A log with a perfect stack still won't become an issue at info or warn.
      • Either error.kind or a valid error.stack. Either alone is enough — which is the useful part, because it means a report site with no Error to hand isn't stuck. error.message is optional but improves grouping.

      A valid stack means at least two lines with at least one meaningful frame — a function name and a file with a position. Passing a real Error gets you kind, message and stack in one go; the matrix rows below that fail are the ones where none of the three arrived.

      When there genuinely is no Error object — a failed validation, a rejected API response — set the attributes yourself and the log still becomes an issue:

      DD_LOGS.logger.error('Checkout rejected', {
  error: { kind: 'CheckoutRejected' },   // enough on its own — no stack needed
  orderId,
})
      Don't set error.kind when you already have an Error. A kind supplied in the context object overrides the one derived from the Error — verified here: a context kind beat a real TypeError while the real stack survived. That swaps an accurate type name for a hardcoded one and degrades issue grouping. Pass the Error and let the SDK fill all three in.

      Fire each source below and read the measured payload — every row shows all three attributes, so a failing row tells you exactly which one was missing. The for Logs column is what works today, pre-consent; the Frontend column stays empty until you grant consent on the Storage inspector tab, which is the coverage gap the Logs pipe exists to fill.

      Recommended shape for a strict-consent deployment
      The obvious architecture doesn't work, and it fails silently. "Cookie-free Logs for errors, cookie-based RUM after consent" is the natural reading of the requirement — but configure the two SDKs with different sessionPersistence values and RUM never establishes a session and sends nothing. No exception, no console warning. Measured in this lab: with RUM on cookie and Logs pinned to local-storage, RUM's beforeSend was never invoked once and getInternalContext() returned undefined. Worth verifying on the customer's SDK version before designing around it.

      Because the storage choice is page-wide, the working shape puts both SDKs on local-storage and gates only RUM behind consent:

      PipeWhen it runssessionPersistenceJob
      Logs → Error Tracking for Logs Always, from first paint
      trackingConsent: 'granted'      		 local-storage
      shared — must match      		 100% error capture, independent of consent
      RUM → Frontend Error Tracking + Replay After consent
      'pending' → setTrackingConsent('granted')      		 Performance, funnels, replays, session counts

      This satisfies every constraint at once, which the split-storage version never could:

      • No cookie, ever — not just pre-consent. Legal's requirement is met by a wider margin than they asked for.
      • No inflated session counts. local-storage survives refreshes and is shared across tabs, so a multi-tab booking flow stays one session — which is what rules out memory as the answer.
      • No coverage gap. Errors reach Error Tracking for Logs from first paint; RUM adds performance and replays once consent lands.

      Once consent is granted both pipes report the same error, which is expected — it's why the matrix shows the two doors separately rather than as a single verdict.

      The one open question is legal, not technical, and it's the same caveat as the Legal topic in the guide: local-storage removes the HTTP cookie, but ePrivacy Art. 5(3) governs "storing information … in the terminal equipment", which several regulators read as covering any client-side storage. If this customer's DPO takes that strict reading, the only remaining cookie-free option is memory for both SDKs — and at that point the session-inflation problem is unavoidable and should be priced into the conversation rather than engineered around.

      Capturing error attributes

      Config alone doesn't get you Error Tracking issues — the call site decides. A log needs a service, an error-level status, and either error.kind or a valid error.stack. These are the exact calls this page makes; the Error capture tab measures what each one produces.

      Automatic — no instrumentation

      forwardErrorsToLogs: true covers uncaught exceptions, unhandled promise rejections and failed requests. All three arrive with a usable stack.

      // nothing to write — these are captured for you
throw new Error('Checkout exploded')
Promise.reject(new Error('Payment provider timed out'))
fetch('https://api.example.com/pay')   // network failure

      Handled errors — pass the Error as the third argument

      This is the one teams miss. The third argument is what populates error.kind, error.message and error.stack; without it the log still reads status:error and still never becomes an issue.

      try {
  submitOrder(order)
} catch (err) {
  DD_LOGS.logger.error('Order submission failed', { orderId: order.id }, err)
  //                    message                   context             Error ◄── required
}

      No Error to pass — set error.kind yourself

      For a rejected API response or a failed validation there may be no Error object. error.kind alone satisfies Error Tracking — no stack needed — and becomes the issue title, so use a real type name.

      DD_LOGS.logger.error('Checkout rejected by provider', {
  error: { kind: 'CheckoutRejected' },   // enough on its own
  orderId: order.id,
  providerCode: res.code,
})

      What not to do

      A kind in the context object overrides the one derived from a real Error, replacing an accurate type name with a hardcoded one and degrading issue grouping. Pass the Error and let the SDK fill all three fields in.

      // ✗ clobbers the real kind — this log groups as 'AppError', not 'TypeError'
DD_LOGS.logger.error(msg, { error: { kind: 'AppError' } }, err)

// ✗ no kind, no stack — a log line forever
DD_LOGS.logger.error('Something went wrong')
console.error('Something went wrong')

      An EU customer's legal team has ruled that no cookie may be created without prior consent — even the first-party RUM session cookie. This lab tests Datadog RUM's cookie-free options against that requirement, live in your browser.

      A common pattern: RUM's session cookie (_dd_s) is created the moment the page loads, before any consent banner is answered. Session Replay is correctly gated behind consent — but the cookie itself isn't, and some EU jurisdictions' ePrivacy enforcement treats any non-essential cookie, including a "technical" monitoring cookie, as requiring consent.

      The tracking-consent API lets you initialize the SDK once — so it's ready to go — without it writing or sending anything until the user answers:

      DD_RUM.init({ ..., trackingConsent: 'pending' })
// later, from your CMP / banner:
DD_RUM.setTrackingConsent('granted')      // starts writing storage + sending data
DD_RUM.setTrackingConsent('not-granted')  // stays fully inert, no storage

      Consent isn't remembered by the SDK across page loads — your app re-applies the user's saved choice (from your own CMP) on every load.

      The banner at the top of the Storage inspector tab drives this live: watch the storage cards stay empty until you click Accept.

      A travel-booking-style flow commonly opens several tabs and refreshes mid-session. That's exactly where memory persistence falls apart: it lives in that one JS heap, so a new tab — or a refresh — has no way to see the old session ID and simply starts a new one.

      The Multi-tab test tab uses a BroadcastChannel to compare the live RUM session ID across every open tab of this page, so you can see the effect directly instead of taking it on faith.

      If the business also wants 100% error capture even pre-consent — event-based capture with no session or storage dependency — RUM itself isn't the right tool for that slice, since it's intentionally gated by consent end-to-end.

      The pattern: run the Logs Browser SDK as an always-on error pipe, and gate only RUM. Note sessionPersistence is the same value in both calls — the two SDKs share one session store, and disagreeing silently stops RUM from sending anything:

      DD_LOGS.init({
  ...
  sessionPersistence: 'local-storage', // cookie-free
  trackingConsent: 'granted',          // always on
  forwardErrorsToLogs: true,
})

DD_RUM.init({
  ...
  sessionPersistence: 'local-storage', // MUST match the above
  trackingConsent: 'pending',          // gated until the user accepts
})

      The requirement is 100% error capture, cookie-free, before any consent is given. Two things to get right.

      First, browser errors reach Error Tracking through two separate front doors. Frontend Error Tracking is fed by the RUM SDK — consent-gated, so unavailable pre-consent. Error Tracking for Logs is fed by the Logs SDK and is the one that works pre-consent, enabled separately for the org.

      Second, sending an error log is not the same as creating an issue. The Logs door needs a service, an error-level status, and either error.kind or a valid error.stack — either of those two alone is enough:

      // becomes an issue — the Error supplies kind + message + stack
try { risky() } catch (err) {
  DD_LOGS.logger.error('Checkout failed', { step }, err)
}

// also becomes an issue — kind alone is enough, no Error needed
DD_LOGS.logger.error('Checkout failed', {
  error: { kind: 'CheckoutFailed' },
})

// stays a log line forever — no kind, no stack
DD_LOGS.logger.error('Checkout failed')
console.error('Checkout failed')

      Hand logger.error a string where the Error belongs and the SDK writes No stack, consider using an instance of Error into the stack field — a diagnostic in a field nobody reads.

      Don't set error.kind when you already have an Error: a context-supplied kind overrides the derived one and degrades grouping. Use it only where there's no Error to derive from.

      Uncaught exceptions, unhandled promise rejections and failed network requests are picked up automatically by forwardErrorsToLogs: true, with usable stacks, and need no instrumentation at all.

      The Error capture tab fires each source and reports what each SDK actually built for it, per front door, so the coverage claim is measured rather than assumed.

      sessionPersistence: 'memory' is cookie-free, but it keeps the session in a JS variable — so every tab and every refresh starts a brand-new session. On a travel-booking site, where multiple tabs and reloads are normal, that inflates session counts against a number the customer actually reports on.

      local-storage is the mode that solves this: cookie-free like memory, but it survives refreshes and is shared across tabs, so a multi-tab booking flow stays one session.

      Note you can't mix — both SDKs share one session store, so sessionPersistence is a page-wide choice. Put both on local-storage and gate only RUM with trackingConsent:

      This is an engineering lab, not legal advice.

      Switching from a cookie to local-storage removes an HTTP cookie — but the EU ePrivacy Directive (Art. 5(3)) governs "storing information, or gaining access to information already stored, in the terminal equipment of a subscriber or user," which several national regulators (including some Nordic DPAs) read as covering any client-side storage mechanism, not literally just cookies named "cookie."

      In other words: a strict regulator may still require consent before writing to localStorage. Confirm the specific jurisdiction's interpretation with the customer's legal/DPO before presenting sessionPersistence: 'local-storage' as a full fix rather than a mitigation.
