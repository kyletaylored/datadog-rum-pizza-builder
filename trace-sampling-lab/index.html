The RUM SDK didn't start, so it can't add trace headers to anything. Requests still reach the pretend backend, which then decides everything on its own. The usual cause is an ad blocker blocking datadoghq-browser-agent.com, or, when running locally, a missing config.js (cp config.template.js config.js).

When your web app calls its own API, RUM can attach trace headers to the request. They do two jobs. They give the backend's trace an ID that RUM also records, so you can jump from a RUM resource straight to its trace. And they tell the backend whether to keep or drop that trace.

Every request makes the same four-stop trip
  1. 01RUM, in the browserDecides whether this session is traced, using traceSampleRate.
  2. 02The requestLeaves with keep headers, drop headers, or none, depending on traceContextInjection.
  3. 03Your backendFollows the browser's decision. With no decision, it uses its own sample rate.
  4. 04DatadogEnds up with a trace linked to RUM, a backend-only trace, or nothing.

Which of your users' API calls end up as traces in Datadog, and which of those can you open from a RUM session? This lab answers that with real requests from your own browser.

traceSampleRate answers "should RUM trace this session?" At 20, about 1 in 5 sessions is traced. Their requests carry a keep decision. The default is 100.

traceContextInjection answers "what about the sessions RUM didn't trace?"

  • 'all': still send trace headers, marked drop. The backend obeys, so those requests are never traced.
  • 'sampled' (default): send no trace headers. The backend never hears from RUM, so it decides on its own.

You might expect traceSampleRate: 20 to trace 2 of every 10 requests. It doesn't. RUM makes the decision from the session ID, so a session is either traced on every request or on none.

The 20% only shows up across many sessions. On the Try it live tab, send a batch, click Start a new RUM session, and repeat. Each row of the Sessions table is one all-or-nothing decision.

Open devtools › Network, filter on api/order, and click a request. A traced request carries two sets of headers that say the same thing:

  • Datadog's: x-datadog-trace-id, x-datadog-parent-id, x-datadog-origin: rum and x-datadog-sampling-priority (1 = keep, 0 = drop)
  • W3C's: traceparent ending -01 (keep) or -00 (drop), plus tracestate

Hover a row in the docked log to see the full traceparent the backend received.

There's no real server. A service worker (sw.js) answers the /api/order calls and follows the same rule a Datadog tracer does:

  • If the request says keep or drop, follow it.
  • If it says nothing, start a new trace and keep it at the backend's own rate (DD_TRACE_SAMPLE_RATE).

Real tracers have extras that aren't modelled here: error and rare samplers that can rescue some dropped traces, and an Agent that can pick rates by itself.

  • Trace headers: the extra HTTP headers RUM adds to an API call so the backend can continue the same trace.
  • Sampling priority: the keep (1) or drop (0) decision carried in those headers.
  • Linked trace: a backend trace that shares its ID with a RUM resource, so you can click from one to the other.
  • Backend-only trace: a trace your backend started and kept on its own. It's in APM, but no RUM resource points to it.
